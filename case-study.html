Every email gets read twice: once by the user, once by the system.

AIEmailer is an AI-powered email security and productivity platform. It reads incoming messages before the user has to — summarizing what matters, flagging what's suspicious, and drafting the reply, all from behind an authenticated, role-aware backend.

01 overview

Three jobs, one inbox.

AIEmailer isn't a single AI feature bolted onto an inbox — it's a small set of workflows, each doing one job well, sitting on top of a backend built to be trusted.

understand

AI summary

Turns a long or dense email into a short, useful summary so the user can decide what to do without reading the whole thread.

protect

Threat analysis

Screens content for phishing-style and suspicious patterns, then surfaces the result as a plain risk signal — not a black box.

respond

Reply assistant

Drafts a context-aware reply using the original email, sender, and a chosen tone. The user reviews and sends — AIEmailer never sends on its own.

02 the problem

The inbox is both information and risk, at the same time.

Reading email is a judgment task disguised as an admin task: is this real, is it important, and what does it actually need from me? AI can help with all three — but only if it's wired into a controlled architecture instead of dropped into the UI as a gimmick.

without AIEmailer

  1. Open and read the message in full
  2. Judge whether it's trustworthy
  3. Pull out what actually matters
  4. Decide on and write a reply

with AIEmailer

  1. Message arrives and is analyzed automatically
  2. Summary and risk signal are shown up front
  3. User reviews the AI's read, not the raw noise
  4. Reply is drafted, then approved by the user
03 system architecture

A backend designed around boundaries, not shortcuts.

Presentation, API orchestration, business rules, identity, persistence, and AI processing are kept separate, so any one of them can change without dragging the others with it.

04 product design

What each workflow actually does.

01

AI summary

Takes the email body plus sender and subject context, and returns a summary built for scanning, not reading. The interface places the raw email on one side and the AI's read of it on the other.

/api/summary/generate
02

Reply assistant

Uses the original message, the sender's name, and a selected tone to produce a draft reply. The user edits and sends it — the assistant proposes, it doesn't act.

/api/reply/generate
03

Threat detection

Looks for phishing-style and suspicious signals in content, and reports the result as a risk indicator a non-technical user can act on — never an unexplained score.

threat-analysis
04

Attachment analysis

A dedicated workflow around attachment metadata, analysis status, generated summaries, and errors — keeping file processing observable instead of a silent step.

attachment-status
05 security & multi-tenancy

AI is only useful if access is controlled first.

Security here is a backend responsibility, not a matter of hiding a button in the UI.

JWT authentication

Protected endpoints require a valid JWT. Authentication is kept separate from authorization, so identity handling can evolve without rewriting business rules.

RBAC & permissions

Roles, permissions, teams, and departments are part of the data model. Permissions are meant to be enforced on the backend — not just by hiding a menu item.

Multi-tenant context

Users and organizations are represented internally with identifiers like uuqid and id_org. Tenant context is resolved server-side, never trusted from client input.

Entra ID, planned

The auth boundary is designed to support Microsoft Entra ID later, while AIEmailer's own users, organizations, and RBAC model stay the source of truth.

The line this project is built around

Authentication answers "who are you?" Authorization answers "what are you allowed to do?" AIEmailer keeps those two questions — and the code that answers them — separate.

07 request lifecycle

What happens when a user asks for an analysis.

01Request arrives

The frontend sends an authenticated request to the relevant API endpoint.

02Identity is established

Middleware validates the JWT and sets up the current user's context.

03Authorization is checked

The backend confirms the user's role and permissions allow this operation.

04The service orchestrates

Input is validated, business rules applied, and the right data or AI path is chosen.

05AI and database work happens

The app talks to SQL Server and, where needed, the Python/AI layer.

06A controlled response returns

Structured output goes back to the frontend for the user to see and act on.

08 challenges

The hard part wasn't adding AI. It was everything around it.

Authentication complexity

Working through JWT, claims and session behavior, protected routes, and a realistic migration path toward Microsoft identity.

Database correctness

Getting tenant/user relationships, stored procedures, permissions, and status handling to hold up under real queries.

Deployment reality

Treating IIS hosting, HTTPS, environment config, Docker, and an Azure path as part of the build — not an afterthought.

09 current state & roadmap

Built in stages, on purpose.

What's implemented and what's planned are kept clearly apart — the point of this project is to reflect real progress, not a finished product.

shippedplanned

Backend foundation

.NET Web API, SQL Server integration, JWT auth, session/identity handling, org-aware design, frontend integration, and a working dev/deploy loop.

Application structure

Dashboard UI, the AI summary and reply assistant workflows, settings/admin concepts, and a backend structured for permission enforcement.

Python AI service

Move AI processing into a dedicated Python service, wired to selected models and production-ready inference.

Microsoft Entra ID

Add Entra behind the existing auth boundary, mapping external identities to internal users while RBAC stays the authority.

Cloud deployment

A staged Azure rollout for the API, database, and frontend — environment secrets, HTTPS, CORS, and CI/CD.

Async processing

Queues and background processing for heavier email or attachment analysis, once load actually calls for it.

10 what this demonstrates

Not "I used AI." More like: I know where AI should sit.

AIEmailer is really a case study in system thinking — identity, authorization, APIs, business rules, data, AI, configuration, deployment, and the user's experience all have to hold together, or none of it matters.
